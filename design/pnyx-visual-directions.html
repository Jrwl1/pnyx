PNYX Visual Direction — Finland-first + Party Scope

This is a revision of the initial visual direction spec. It retains Direction A ("The Public Record") — the editorial visual system, Fraunces + Source Sans 3 + warm parchment palette — and regenerates all information architecture, page specs, and mockups to align with the locked canon.

What changed from v1

1. Finland-first scope. All placeholder content is now Finnish: Eduskunta members, Finnish parties (Kokoomus, SDP, Perussuomalaiset, etc.), Finnish constituencies. No U.S. offices or regions.

2. Party as a first-class entity. New routes: /parties and /parties/:id. Nav updated: Home | Politicians | Parties | Methodology.

3. Party stance records. Party-level stances are tracked separately from politician promises. Party profiles show official positions; politician profiles show where an individual aligns or breaks from their party line.

4. Fulfillment + vote-alignment framing restored. The v1 spec introduced "evidence confidence" framing that conflicted with FRONTEND_V3_SPEC.md. This version uses the spec's fulfillment/vote-alignment semantics. See the open decision below.

5. Methodology updated. No longer claims PNYX "does not categorize politicians by party." Party context is now central to the product.

Product summary

PNYX is a public-interest tool for political accountability, launching first in Finland. Named after the hill in Athens where citizens assembled to hold leaders accountable, PNYX lets ordinary people find a politician or party, review public promises and official stances, inspect source evidence, compare a politician's record against their party line, and understand what is known vs. unknown.

Finland's multi-party parliamentary system makes party context essential. A politician's promises exist in relation to their party's official stances — and where a politician breaks from party line is often the most interesting signal for voters.

Primary audience

Finnish citizens. Ordinary voters who want to see what their representatives and parties have committed to, and what the evidence says.

Core entities

Politicians, parties, promises (politician-level), stances (party-level), evidence items. Party and politician are separate first-class entities with their own pages.

Key relationships

A politician belongs to a party. A promise belongs to a politician. A stance belongs to a party. A politician's promise can align with, contradict, or be unrelated to their party's stance on the same issue.

Data honesty

Fulfillment and vote alignment default to "Unknown / Data not yet available" where backend data is missing. Community sentiment is clearly labeled as user votes, not official record.

Open decision — needs canon ruling

Fulfillment framing vs. evidence-confidence framing

⚠ This requires an explicit decision before implementation

The V3 frontend spec (FRONTEND_V3_SPEC.md) defines fulfillment status (fulfilled / broken / in_progress / unknown) and vote alignment (aligned / contradicted / mixed / unknown) as the primary status dimensions. This is what the shipped frontend implements.

However, the reality is that all fulfillment and vote-alignment data is currently "unknown" because the backend provides neither fulfillment assessments nor roll-call vote data. The v1 design spec proposed reframing these as "evidence confidence" (well-documented / partially documented / insufficient evidence / contradicted) which maps to what the backend actually provides (verification status).

This v2 spec follows the current canon (fulfillment + vote-alignment framing) and renders those surfaces with "Unknown / Data not yet available" where data is missing. But the design includes a note on every affected surface marking where the evidence-confidence framing might better serve users once this decision is made.

Option A: Keep fulfillment framing (current canon)

Show "Fulfilled / Broken / In progress / Unknown" on profiles and promises. Most will read "Unknown" at launch. Ship empty surfaces now; populate as data arrives. This is honest but might feel sparse.

Option B: Use evidence-confidence framing

Show "Well-documented / Partially documented / Insufficient evidence / Contradicted" based on verification status, which the backend already provides. This gives users useful signal from day one, but changes the product semantics.

This spec does not resolve this question. It flags it and follows current canon (Option A) throughout. If Option B is chosen, the mockups would change the status chips and methodology definitions but not the layout, typography, or visual system.

Implementation notes

Implementation guidance

New components needed

PartyChipRow (home), BrowseByParty (home), PartyCard (party directory + home), PartyStanceCard (party profile), PartyLineComparison (politician profile), PartyStanceContext (promise detail). Plus TrustStrip, MethodologyCallout, StepCard from v1.

Data model implications

Requires: party table, party_stances table, politician-party foreign key, and potentially a politician_party_alignment junction. API needs /parties and /parties/:id endpoints. These are identified in backlog items B-102 through B-105.

Migration from V3

Visual system (fonts, colors, grid) stays identical. Nav adds one item. Politician pages add party-context sections but keep existing structure. Two new routes added. Methodology page adds sections. Estimated: medium effort — the visual work is minimal, the IA work is the bulk.

Launch-state honesty

At launch, most fulfillment/alignment/party-alignment data will be "Unknown." Design every surface to look intentional and informative in that state, not broken. The "Unknown / Data not yet available" pattern must feel like a feature of transparency, not a bug.
